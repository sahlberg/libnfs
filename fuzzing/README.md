# Fuzzing libnfs

libFuzzer target for the RPC reply decoding, i.e. everything a server
sends back to the client. Not part of the normal build, nothing else in
the tree depends on it.

The harness feeds a buffer to one of the generated ZDR reply decoders,
picked by the first input byte, the same dispatch rpc_process_pdu uses
when it hands a reply to the per procedure decoder. All 157 of them are
covered: NFS v2/v3, mount v1/v3, NLM, portmap v2/v3, rquota and the
NFSv4.x compound, so the deep structures (READDIRPLUS3, fattr3, NFSv4
operations and attributes) get reached too.

Build libnfs first, without the optional TLS, Kerberos and RDMA
support so the static library needs nothing beyond -lpthread, then the
target:

    cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -DBUILD_SHARED_LIBS=OFF \
      -DENABLE_TLS=OFF -DENABLE_KRB5=OFF -DENABLE_RDMA=OFF
    cmake --build build -j$(nproc)

    clang -std=c11 -g -fsanitize=fuzzer,address -fno-omit-frame-pointer \
      -I include -I include/nfsc -I nfs -I mount -I nlm -I rquota -I portmap -I nfs4 -I build \
      fuzzing/libnfs_reply_fuzzer.c build/lib/libnfs.a -lpthread \
      -o libnfs_reply_fuzzer

Run it over the seeds:

    ./libnfs_reply_fuzzer fuzzing/seeds/

seeds/ is a small corpus spread across the decoder table.

The idea is to hook this up to OSS Fuzz so it keeps running there
under sanitizers continuously.

## Socket-level fuzzers

These targets drive the transport itself instead of a single decoder.
Each one attaches an rpc_context to one end of a socketpair and writes
the fuzz input to the other end, so the bytes go through rpc_service(),
record marking, fragment reassembly, XID matching and the callbacks, the
same way they would from a real peer:

- libnfs_rpc_reply_stream_fuzzer: the client side. One NFSv3, mount or
  portmap request is sent, then the input is the server's reply stream.
- libnfs_rpc_server_call_fuzzer: the server side
  (rpc_init_server_context). The NFS, mount, portmap, NLM, NSM, rquota and
  NFSACL programs are registered, and the input is the client's stream of
  CALLs.
- libnfs_nfs3_read_zero_copy_fuzzer: the client zero-copy READ path
  (rpc_nfs3_readv_task), where the reply data is placed straight into the
  caller's iovecs. The input is the server's reply to one READ.

The first input bytes are control bytes, such as how the input is
chunked into writes; see the "Input layout" comment at the top of each
file. With libnfs built as above:

    for f in libnfs_rpc_reply_stream_fuzzer \
             libnfs_rpc_server_call_fuzzer \
             libnfs_nfs3_read_zero_copy_fuzzer; do
      clang -std=c11 -g -fsanitize=fuzzer,address -fno-omit-frame-pointer \
        -I include -I include/nfsc -I nfs -I nfs4 -I mount -I portmap \
        -I nlm -I nsm -I rquota -I build \
        fuzzing/$f.c build/lib/libnfs.a -lpthread -o $f
    done

    ./libnfs_rpc_reply_stream_fuzzer -dict=fuzzing/libnfs_rpc_reply_stream_fuzzer.dict \
        fuzzing/seeds_rpc_reply_stream/

Each fuzzer has a dictionary, fuzzing/<fuzzer>.dict, and a seed corpus,
fuzzing/seeds_<name>/, generated by gen_stream_seeds.py:

    python3 fuzzing/gen_stream_seeds.py fuzzing

## Client operations fuzzer

libnfs_client_ops_fuzzer.c drives the high-level client (lib/libnfs.c,
lib/nfs_v3.c, lib/nfs_v4.c) through the public async API. It mounts an
export with nfs_mount_async() and then runs up to four operations chosen
by the input (stat, open, read, write, opendir, readlink, rename, locks,
ACLs, ...). The fuzzer plays the server: it reads each CALL the client
sends, copies its XID, and answers with the next reply from the input, so
the input decides the content of every portmapper, mount, NFSv3 and NFSv4
COMPOUND reply without having to guess XIDs. On NFSv4.1 and 4.2 the input
can also send CB_COMPOUND calls on the back channel.

The client has to open its own TCP connections for this, so the fuzzer
is linked with -Wl,--wrap for socket(), connect(), bind(), setsockopt(),
dup2() and getservbyport(): the calls libnfs makes go to __wrap_socket()
and friends in the fuzzer, which hand out one end of a socketpair instead
of a TCP connection. Nothing in libnfs is changed and no network is used.
--wrap is a GNU ld / lld option, so this fuzzer is Linux only.

The same source is built once per NFS version, selected with
-DFUZZ_NFS_VERSION (3, 40, 41 or 42). With libnfs built as above:

    for v in 3 40 41 42; do
      clang -std=gnu11 -g -fsanitize=fuzzer,address -fno-omit-frame-pointer \
        -DFUZZ_NFS_VERSION=$v \
        -I include -I include/nfsc -I nfs -I nfs4 -I build \
        -Wl,--wrap=socket -Wl,--wrap=connect -Wl,--wrap=bind \
        -Wl,--wrap=setsockopt -Wl,--wrap=dup2 -Wl,--wrap=getservbyport \
        fuzzing/libnfs_client_ops_fuzzer.c build/lib/libnfs.a -lpthread \
        -o libnfs_nfs${v}_client_ops_fuzzer
    done

The four binaries share the dictionary. The seed corpora are not kept in
the tree; gen_client_ops_seeds.py writes them, one directory per binary
(seeds_nfs3_client_ops/, seeds_nfs40_client_ops/, ...). Every seed is a
whole conversation with a well-behaved server (mount, then the
operations):

    python3 fuzzing/gen_client_ops_seeds.py build

    ./libnfs_nfs3_client_ops_fuzzer -dict=fuzzing/libnfs_client_ops_fuzzer.dict \
        build/seeds_nfs3_client_ops/
